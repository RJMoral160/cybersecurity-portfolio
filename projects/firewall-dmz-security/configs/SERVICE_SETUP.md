# Isolated DMZ service setup

`reference-implementation` for AlmaLinux/RHEL-style VMs, not a command transcript. Use one DMZ server per firewall. Install `httpd`, `vsftpd`, `firewalld`, and, only on the VyOS side, a TFTP server package. Verify package/service names and release (`cat /etc/os-release`, `httpd -v`, `vsftpd -v`, `firewall-cmd --version`) before copying files. Never run this on a host attached to an untrusted production network.

1. Assign pfSense-side server `192.168.3.10/24` with gateway `192.168.3.1`, or VyOS-side server `172.18.37.10/24` with gateway `172.18.37.1`. Confirm DNS and routing independently. Put [Apache virtual host](apache-vhost.conf) in the distribution's `/etc/httpd/conf.d/` directory and a harmless index/health page in its configured document root. Use `apachectl configtest`, then start `httpd`. Do not assume a pfSense GUI response means the DMZ server was reached; check the HTTP `Server` header, content, and firewall state.
2. Install the matching [pfSense vsftpd](vsftpd-pfsense.conf) or [VyOS vsftpd](vsftpd.conf) reference at `/etc/vsftpd/vsftpd.conf`. Back up the package default privately first. Create a dedicated, nonprivileged local `labftp` account and a root-owned read-only directory containing `hello.txt`; configure its home and PAM/shell access according to the distribution. Do not reuse an administrator account or publish its password. With `write_enable=NO`, uploads should fail. Set a strong local-only password through the system password tool, then check `vsftpd` service logs without exposing authentication data.
3. Keep `firewalld` and SELinux enabled. On the pfSense DMZ VM allow TCP 80,21,50000-50100; on the VyOS DMZ VM allow TCP 80,21,30000-30100 and the TFTP service only if installed. Example persistent commands for the pfSense-side host are `firewall-cmd --permanent --add-port=80/tcp`, `--add-port=21/tcp`, and `--add-port=50000-50100/tcp`, followed by `firewall-cmd --reload` and `firewall-cmd --list-all`; substitute the VyOS range on that host. Restrict the host zone to the expected interface/source where supported. Inspect `getenforce`, `ausearch -m AVC -ts recent`, and local SELinux policy/port labels before applying a narrow `semanage port` adjustment for a denied service. Do not use permanent `setenforce 0` or disable the host firewall as a fix. See [Red Hat's network service guidance](https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/8/html/securing_networks/assembly_securing-ftp_securing-networks).
4. TFTP has no login and begins at UDP 69, then uses negotiated transfer IDs. Serve only a harmless read-only file from a dedicated root; keep its daemon and UDP host rule limited to the isolated VyOS DMZ. Confirm VyOS conntrack's TFTP helper is available on the chosen 1.5 image or use a controlled explicit transfer-port design. Do not infer a transfer from a UDP 69 reachability check.
5. From `203.0.113.10` test `curl --fail http://203.0.113.6/` (pfSense) and `curl --fail http://172.18.37.10/` (VyOS routed test network). For FTP, use an isolated client with passive mode and run a directory listing and `hello.txt` download via `ftp 203.0.113.6` or `ftp 172.18.37.10`; inspect the chosen passive port in client debug output, firewall state, and vsftpd log. Attempt a test upload and expect denial. Test TCP 22 to the **DMZ server** as a denied flow; separately test firewall-management access from an unapproved address. No output in this guide is represented as an original run.

Rollback: restore the VM snapshot and original service config, remove only the test-specific firewall/NAT rules, and verify the default block and service shutdown before reconnecting a VM to any other network. Never delete the sole copy of logs needed to diagnose a failed transfer.
