# BIND DNSSEC lab workflow

`reference-implementation` for **BIND 9.20.2**. The historical project used manual signing and later inline signing; this file specifies one reproducible *new-lab* method using BIND's `dnssec-policy default`. It does not claim that a validating-resolver result was preserved from the original lab. Use an isolated resolver and authoritative server: `example.org` and RFC 5737 addresses here must never be advertised or queried on the real Internet. ISC's [BIND 9.20.2 DNSSEC chapter](https://bind9.readthedocs.io/en/v9.20.2/chapter5.html) describes the policy and key lifecycle.

1. Install BIND 9.20.2 and DNS utilities on the isolated primary, secondary, and a separate validating resolver. On an RPM-style system the primary file is `/var/named/example.org.zone`; place [named-primary.conf](named-primary.conf) in the isolated `named.conf` include tree. Create `/var/named/keys` owned by the `named` service account with mode `0700`; the generated `.private` and `.state` files stay there, outside Git. The `named` account also needs write access and an appropriate SELinux context for the inline-signed zone and journal beside the unsigned zone; verify the distribution's writable-zone layout before startup. Do not copy a private key into this repository.
2. Check `named-checkconf` and `named-checkzone example.org /var/named/example.org.zone`, then start/reconfigure `named`. The zone's `dnssec-policy default; inline-signing yes;` causes BIND to **generate** its own signing key(s) and maintain a separate `.signed` zone. Inspect key metadata with `rndc signing -list example.org`, `rndc zonestatus example.org`, and a local directory listing of `Kexample.org*.key` (public key files) and `.private` (private; never display or publish). Confirm `dig @198.51.100.10 example.org DNSKEY +dnssec` and `dig @198.51.100.10 mail.example.org A +dnssec` show DNSKEY/RRSIG. This proves serving signed records, not chain validation.
3. Establish trust **inside the isolated lab**. Generate DS text from the newly generated public key with `dnssec-dsfromkey -2 /var/named/keys/Kexample.org.+<algorithm>+<id>.key`. Obtain the actual filename locally rather than copying the placeholder. In a lab parent zone, publish that DS and delegate to `ns1`/`ns2`; alternatively, on a dedicated local validating BIND resolver, configure `trust-anchors { "example.org" static-ds <key-tag> <algorithm> <digest-type> "<hex-digest>"; };` using the exact generated DS fields. Set `dnssec-validation yes;`, `recursion yes;`, `allow-recursion { 127.0.0.1; };`, and an isolated forward zone for `example.org` pointing only to `198.51.100.10/11`. Keep this resolver off the Internet. ISC's [trust-anchor reference](https://bind9.readthedocs.io/en/v9.20.2/reference.html) defines `static-ds` field order. A static local anchor must be updated during key rollover; an actual public deployment uses controlled parent delegation instead.
4. Query the **resolver**, not only the authoritative server: `dig @127.0.0.1 mail.example.org A +dnssec`. Expect the AD flag only after the trust chain and resolver validation succeed. Query a deliberately tampered *copy* of a signed zone in another isolated test instance and expect SERVFAIL; do not damage the working zone just to produce a result. Record resolver logs and DS/key IDs privately. A successful authoritative RRSIG response without AD is insufficient.
5. For updates, edit the unsigned source file, increment the SOA serial beyond the value currently served (including the secondary's current serial), run `named-checkzone`, then `rndc reload example.org`. BIND maintains fresh signatures on the inline-signed copy. Check `dig @198.51.100.10 example.org SOA +short`, `dig @198.51.100.11 example.org SOA +short`, `rndc signing -list example.org`, and the validating resolver's AD result. The secondary initiates TCP 53 AXFR/IXFR after notification or refresh; allow that source in `allow-transfer` and the firewall.
6. For rollback, restore **content** from the prior known-good unsigned zone but set a *newer* SOA serial before reload. Wait for regenerated signatures and secondary transfer, then repeat resolver validation. Restoring an old file with an old serial can leave the secondary stale and signatures inconsistent. Back up the key directory privately; do not casually replace or regenerate signing keys during a content rollback.

The `dnssec-policy` path replaces the incomplete manual-key commands that were previously shown as if they were a complete workflow. It supplies generation, serving, local trust, validation, updates, and rollback, but was not executed against a live BIND installation in this repository. No DS was published to a real parent zone.
